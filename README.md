# 星勢 StarMomentum

> 看準勢頭，發現下一顆新星。

「勢」是動能：排名看的是 star 增長的速度和加速度。本項目與 GitHub 並無關聯。

每日用 GitHub 公開資料找出正在上升的 repository，以可解釋分數排序，再產生中文研究摘要。

## 功能

- 今日 Top 50、分類篩選與即時搜尋
- 首三名重點研究，其餘保持高密度列表
- 每個 repo 顯示上榜原因、適合對象、證據、風險與分數拆解
- 每日 JSON 歷史、原始快照和 Markdown 日報
- 首日暖機，第二次快照開始使用真實 24 小時增長
- 每日香港時間 08:00、16:00、24:00 自動更新及部署 Pages：由外部排程服務（cron-job.org）準時觸發 GitHub Actions。GitHub 自帶排程（07:47、15:47、23:47）實測會遲 3 至 7 小時，只作後備；若網站 6 小時內已更新，後備會自動跳過。
- API 或驗證失敗時不會覆蓋上一份正常網站

## 本機使用

```bash
pnpm install
pnpm run daily
pnpm dev
```

公開資料可以不帶 token 執行，但額度較低。需要時把 GitHub token 放入 `GITHUB_TOKEN` 環境變數。不要把 token 寫進程式或提交到 Git。

無網絡時可以建立明確標示的示例榜：

```bash
pnpm run daily:fixtures
```

## 驗證

```bash
pnpm test
pnpm build
```

## 排名方法

有每日基線後，100 分由以下訊號組成：

- star 動能 35 分
- 按 repo 體量校正的相對增長 20 分
- 相比前六日的增長加速度 10 分
- fork 動能 10 分
- 最後 push 距今時間 15 分
- 項目年齡新鮮度 10 分

增長訊號的估算方式：

- 增量除以兩份快照的實際相隔時間，換算成每日速度；Actions 延遲或漏跑都不會令數字失真。
- 若 repo 不在昨日快照，會改用四日內最近一份包含它的快照。
- 每日三次更新會覆蓋當日快照，基線只取前幾日的快照；排名升跌則對比上一次更新。
- star 速度取 24 小時速度與三日平均各半，減少單日噪音。
- 在上一份快照之後才建立的 repo，所有 stars 都算作期間增長。
- 完全沒有基線的 repo 多數是因為正在上升才剛進入候選池，所以用候選池第 70 百分位的速度，不會被當成零增長而埋沒。
- 同分訊號共用平均百分位，不受 API 回傳次序影響。
- 一星期新增超過 200 stars、但新增 forks 不足 stars 3% 的 repo 會顯示刷星提醒（一般 repo 約 10%）。提醒不影響分數，因為收藏型清單亦常見這種比例。

首日沒有昨日數據，會以 stars/day、總 stars、項目年齡和最後 push 建立暖機排名。摘要文字不參與分數。

### 回測

```bash
pnpm backtest
```

用每日快照重播排名（只用當日已有的歷史），再對比之後 1、3、7 日實際的 star 增長（絕對增長 60%、體量校正增長 40%）。指標包括 Spearman 相關、Top 50 命中率和前後兩日 Top 50 重疊度。以下以 2026-09-02 至 10-05 的 34 份快照回測，以未來 3 日為準：

| 版本 | Spearman | Top 50 命中率 | Top 50 穩定度 |
| --- | --- | --- | --- |
| 1.0.0 | 0.688 | 0.527 | 0.699 |
| 1.1.0 | 0.853 | 0.608 | 0.714 |
| 1.2.0 | 0.859 | 0.618 | 0.708 |

#### 防偷看未來與基準比較（2026-10-31 起）

回測已收緊兩點：第 t 日的 Top 50 在看未來數據前就固定，之後跌出候選池的項目當作未命中，不再由下一名補上；所有正規化只用第 t 日或之前的快照。修正後 3 日命中率由 0.632 降至 0.607，即舊數字約高估 2.5 個百分點。

新增指標：命中率相對隨機抽選的倍數（lift）、按 star 數三等分後各組內的 Spearman、NDCG@50，以及「突破」命中倍數（未來每日增長 ≥ 過去一週兩倍且每日 ≥ 10 stars）。並以三個公開或文獻基準對照。以下為 2026-09-02 至 10-31 共 60 份快照、未來 3 日的結果：

| 排名方法 | Spearman | 組內 Spearman | Top 50 命中率 | 倍數 | NDCG@50 | 突破倍數 |
| --- | --- | --- | --- | --- | --- | --- |
| 現行方法 | 0.855 | 0.825 | 0.607 | 8.61 | 0.891 | 2.08 |
| OSS Insight 式 7 日加權 | 0.793 | 0.784 | 0.585 | 8.30 | 0.902 | 1.98 |
| 純 3 日速度 | 0.617 | 0.617 | 0.565 | 8.02 | 0.887 | 2.00 |
| 3 日對數增長率 | 0.505 | 0.584 | 0.321 | 4.56 | 0.596 | 2.61 |

現行方法在 Spearman 和命中率上勝過所有基準；OSS Insight 式公式的 NDCG 和穩定度略高，7 日目標上兩者接近。對數增長率最能捉到細項目「翻倍」，但整體排名明顯較差。`pnpm backtest` 可加方法名稱只跑指定項目，例如 `pnpm backtest production`。

1.2.0 的改進經配對 bootstrap 檢定，未來 1 日和 3 日的 Spearman 及命中率提升都顯著（95% 信賴區間不含 0）；3 日穩定度變化不顯著。

權重沒有按回測調整，避免以少量歷史過度擬合；只改進訊號的估算方式。

已回測但沒有採用的方法：

- SigniTrend 式 z-score（今日增長對比自身 EWMA 基線）取代加速度：命中率和穩定度都下降，因為它偏好單日爆升。
- Gamma-Poisson 經驗貝氏收縮取代 `sqrt(stars+25)` 體量校正：命中率略降。2026-10-31 再以「後驗平均減一個標準差」收縮 star 速度重測，3 日命中率 0.603 對 0.607，同樣沒有改善。
- 分數按前一日平滑：穩定度明顯上升，但命中率下降約 3 個百分點，屬取捨而非改進。

## 分類

共 11 個分類加「其他」：AI、開發工具、Web、資料、雲端與基建、安全、手機應用、桌面與系統、設計與多媒體、遊戲、學習資源。

- 規則按證據加權：作者自訂的 topics 最重，名稱和描述次之，主要語言只作輕微參考。
- 只配對完整字詞，`ide` 不會誤中 `video`；`list`、`port` 這類在句子中常見的字只在 topics 出現時才算。
- 中文描述用關鍵字配對，例如「指南」、「遊戲」、「輸入法」。
- 每個 repo 最多兩個分類，最強的排第一；第二個分類的證據要有第一個的一半以上。
- 以歷史榜單 414 個項目檢驗，歸入「其他」的由 94 個減至 49 個，剩下大多沒有描述。
- 設定了 Jev 時，Top 50 以 Jev 的判斷為準，規則作後備。

## Jev 分類與風險提示

Top 50 的分類和風險提示交由 TypeSafe 的 [Jev](https://docs.typesafe.ai/) 模型判斷。Jev 不生成文字，只會在固定的分類選項中選一個，並給出每個選項的機率。

- 每個 repo 問一條選擇題：根據名稱、描述、語言和 topics，它最屬於哪個分類。題目明確要求看項目做甚麼，而不是用甚麼語言寫、支援哪些平台。
- 選擇題選出主分類。由於一個項目可能同時屬於幾類，同一個請求裏每個分類另有一條是否題（TypeSafe 的 Noul），「是」的機率達 60% 或以上的最高一項列為第二分類。60% 是起始值，會按實際運行結果調整。
- 沒有描述也沒有 topics 的 repo 不問 Jev，因為只看名稱只能靠估。
- 需要 GitHub repository secret `TYPESAFE_API_KEY`。沒有 key、key 無效或請求失敗時，自動沿用關鍵字規則。
- 每次運行的日誌會記錄成功數目，以及 Jev 與規則主分類一致的比例，方便核對。
- 同一個請求另有六條風險是否題：盜版／破解、洩漏內容、成人內容、加密貨幣推廣、繞過付費服務、可被濫用（惡意程式、攻擊或監控工具）。「是」的機率達 70% 或以上就在列表顯示黃色標記，並在「採用前注意」加一句說明。70% 是起始值，每次運行的日誌會列出命中的項目和機率，方便核對及調整。
- 風險提示只作提醒：被標記的項目照樣留在榜上，分數和排名不變。
- 設 `JEV=off` 可停用，設 `TYPESAFE_DEFAULT_MODEL` 可改用其他模型（預設 `jev-latest`）。
- 分類只用於篩選和「適合誰」，不影響分數和排名。

## 刷星偵測

研究顯示刷星相當普遍：ICSE 2026 論文〈Six Million (Suspected) Fake Stars on GitHub〉估計，2024 年 7 月當月達到 50 stars 的倉庫中約 16.7% 涉及刷星，而且主要出現在動能排名最顯眼的尖峰。每次更新會為 Top 50 中 50 stars 以上的項目，經 GitHub GraphQL 抽樣最近 100 個加星帳戶：

- 「空殼帳戶」：公開倉庫 ≤ 4、追隨者 ≤ 1、個人資料全空（Dagster 2023 買星實驗的特徵）。
- 可疑帳戶：在加星前 30 日內才建立的空殼帳戶，或同時為 3 個以上當日上榜項目加星的空殼帳戶（StarScout「同步加星」的簡化版）。
- 可疑帳戶 ≥ 15 個且佔抽樣 ≥ 25% 時標記「疑似刷星」，並在「採用前注意」說明比例；抽樣乾淨（< 10%）時移除較粗糙的 fork 比例提示。
- 門檻刻意保守，每個項目的抽樣數字都寫入運行日誌，累積實際分佈後再校準。只作提示，不影響分數和排名；設 `STAR_AUDIT=off` 可停用。

## Hacker News 曝光

外部曝光是 star 爆升的主因（例如 Fang 等人 ICSE 2022 估計每輪推文爆發約令 stars 增加 7%）。每次更新以免費的 HN Algolia API 查找過去 14 日連結到 Top 50 項目的 Hacker News 帖子，最高分的一則會以「HN 分數」標籤和研究摘要中的證據顯示，方便讀者知道升幅從哪裏來。只作參考，不影響排名；設 `HACKER_NEWS=off` 可停用。

## 每日資料流

1. 九組搜尋分別探索新項目、活躍項目及主要技術分類。
2. 合併並去除重複、fork 和 archived repository。
3. 與最近八日快照比較，計算增長和排名變化。
4. Top 50 交由 Jev 判斷分類和風險，再抽樣檢查加星帳戶及查找 Hacker News 帖子；任何一步失敗都只會略過該步。
5. 寫入 `public/data/current.json`、日期歷史、候選快照及 Markdown 日報。
6. 測試及建置全部通過後才提交資料並部署 Pages。

## GitHub Pages

把專案推到 GitHub 後，在 repository Settings 的 Pages 將來源設為 GitHub Actions。工作流亦可由 Actions 頁面手動執行。

若預設分支禁止 Actions bot 直接 push，請允許 `github-actions[bot]` 寫入資料，或把保存歷史步驟改為建立 pull request。
